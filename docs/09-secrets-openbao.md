# 09 · Secrets with OpenBao (open-source Vault)

## Why OpenBao and not Vault

HashiCorp moved Vault from MPL 2.0 to the **Business Source License** in August 2023 (not open source: no competing
offerings). **OpenBao** is the community fork of the last MPL release (Vault 1.14), governed by the Linux Foundation /
OpenSSF, API-compatible with Vault (same HTTP API, `X-Vault-Token` header, KV v2, AppRole, policies, Agent), and
it now ships features that are Enterprise-only in Vault (namespaces, horizontal read scaling). This repo runs
`openbao/openbao:2.6.2`. Everything here applies to Vault with `vault` instead of `bao`.

## The mental model

```
                  ┌──────────────── OpenBao ─────────────────┐
   who are you?   │  auth methods  ──► token (TTL, policies)  │
   (identity)     │  approle · kubernetes · oidc · userpass   │
                  │                                            │
   what may you   │  policies (HCL): path + capabilities       │
   do?            │  path "secret/data/ec2-lakehouse/s3" { capabilities = ["read"] }
                  │                                            │
   the secrets    │  secrets engines mounted at paths          │
                  │  kv-v2 (static, versioned) · database (dynamic creds) · pki · transit (encrypt/sign) · aws
                  │                                            │
   storage        │  raft (integrated) ── encrypted at rest; "sealed" until unsealed with key shares / KMS
                  └────────────────────────────────────────────┘
```

1. **Sealed / unsealed**: on start the server can't decrypt its storage. Unsealing provides the master key (Shamir key
   shares, or **auto-unseal via a cloud KMS** in production).
2. **Auth method** → **token**: every client logs in somehow and receives a short-lived token carrying **policies**.
3. **Policies** grant capabilities on paths. Default deny.
4. **Secrets engines**: KV for static secrets; *dynamic* engines mint credentials on demand that expire (a fresh
   Postgres user per pod, AWS STS creds), so there's nothing long-lived to leak.
5. Everything is **audited** (enable an audit device in production).

## How this stack uses it

| Secret (KV v2 at `secret/ec2-lakehouse/…`) | Generated by | Read by (policy) |
|---|---|---|
| `s3` (access key, secret key) | `init_openbao.py`, random | pipeline, api, developer |
| `api` (RSA private key that signs JWTs) | random 2048-bit key | api only |
| `admin` (API admin password) | random | api, developer |
| `mcp-client` (OAuth client secret for token exchange) | random | api, mcp |
| `agent` (API user the agents log in as) | random | api, developer |
| `anthropic` (your Claude API key) | **you**: `mise run set-anthropic-key` | developer |

Flow on `mise run up`:

1. **`openbao`** starts sealed, Raft storage on a volume.
2. **`bao-init`** ([scripts/init_openbao.py](../scripts/init_openbao.py), idempotent): initializes (first time only),
   unseals, enables KV v2 + AppRole, writes policies, **generates secrets with check-and-set 0** (never overwrites),
   creates one **AppRole per workload** and drops its `role_id`/`secret_id` into a per-service folder of the
   `bao-creds` volume, renders SeaweedFS's `iam.json` from the S3 secret, and writes a developer token to
   `./.bao/dev-token` for code you run on the laptop.
3. Each service mounts **only its own** creds folder (compose `volume.subpath`) and starts through
   [scripts/bao_exec.py](../scripts/bao_exec.py): AppRole login → read the listed secrets → set env vars → **revoke its
   token** → `exec` the real process. The app just reads env vars (12-factor); it doesn't know OpenBao exists.
4. The API signs tokens with the private key; it publishes the **public** key at `/.well-known/jwks.json`, so the MCP
   server verifies tokens **without any shared secret**.

Try it:
```bash
export BAO_ADDR=http://localhost:8200 BAO_TOKEN=$(cat .bao/dev-token)     # mise sets BAO_ADDR for you
curl -s -H "X-Vault-Token: $BAO_TOKEN" $BAO_ADDR/v1/secret/data/ec2-lakehouse/admin | jq .data.data
curl -s -H "X-Vault-Token: $BAO_TOKEN" $BAO_ADDR/v1/secret/data/ec2-lakehouse/api        # 403: least privilege
mise run admin-password                                                                   # same, via Python
open http://localhost:8200/ui      # log in with the dev token
```

## What's deliberately local-only (and the production version)

| Here | Production |
|---|---|
| 1 unseal key + root token in a Docker volume | **KMS auto-unseal** (`seal "awskms"`), root token revoked after bootstrap, break-glass via recovery keys held by several people |
| TLS off | TLS everywhere, mTLS between services |
| AppRole `secret_id` files on a volume | **Kubernetes auth method**: pods log in with their ServiceAccount token, no secret-zero file |
| `bao_exec.py` reads at start | **OpenBao Agent** sidecar (renders templates, renews tokens, live reload) or the **External Secrets Operator** syncing into Kubernetes Secrets |
| Static S3 keys in KV | dynamic credentials (AWS secrets engine → STS), or no secret at all: **IRSA / EKS Pod Identity** |
| Developer token file | `bao login -method=oidc` through your IdP |
| Postgres/Lakekeeper bootstrap passwords in compose | dynamic **database** secrets engine (per-pod Postgres users with TTL) |

**Secret zero**: something has to authenticate to the secrets manager. The production answer is to let the *platform*
vouch for the workload (Kubernetes ServiceAccount tokens, AWS IAM, GitHub OIDC) — the same idea as identity
federation for the Claude API ([08](08-production-agents.md#no-api-keys-workload-identity-federation)). OpenBao then
only holds what can't be federated.

**OpenBao vs AWS Secrets Manager** for your platform: on all-AWS, Secrets Manager + IRSA + ESO is less to run.
OpenBao earns its keep when you need dynamic secrets across many systems, PKI, transit encryption/signing, multi-cloud,
or on-prem (your DCIM/Ansible side).

## A real-world incompatibility found while building this

Lakekeeper can store warehouse storage credentials in Vault KV v2 (`LAKEKEEPER__SECRET_BACKEND=kv2`) instead of
Postgres. Against OpenBao 2.6.2 it fails its health check: its Vault client library requires a `performance_standby`
field in `/v1/sys/health` that OpenBao doesn't return. "API-compatible fork" means *mostly* compatible: test the
integrations you depend on. Lakekeeper here keeps them in Postgres, encrypted with `PG_ENCRYPTION_KEY`.
