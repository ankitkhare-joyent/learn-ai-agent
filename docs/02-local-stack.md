# 02 · The local stack, and how it maps to AWS

```
 laptop ──► agents (raw loop · LangGraph · Strands · skills) ──Claude API──► claude-opus-5-5
              │ MCP over HTTP (Bearer, aud=ec2-mcp)
              ▼
         mcp :8001  ──token exchange──►  api :8000 (FastAPI + DuckDB, hot cache)
                                          │ Iceberg REST            │ S3 reads
                                          ▼                         ▼
                                   lakekeeper :8181 ◄─► postgres   seaweedfs :9000 (S3)
                                                                     ▲
                       seed: generate_raw (zstd Parquet) ─► load_iceberg (PyIceberg) ┘
         openbao :8200 ── every container gets its secrets at start (AppRole) ──►  all of the above
```

| Local | Typical production | Notes |
|---|---|---|
| SeaweedFS (S3 API) | Amazon S3 | MinIO's images left Docker Hub in 2025; SeaweedFS is Apache-2.0 and runs natively on Apple Silicon. RustFS 1.0 (Oct 2026) is a newer MinIO-like option. |
| Lakekeeper (Iceberg REST catalog) + Postgres | AWS Glue Data Catalog (or S3 Tables) | Glue and S3 Tables both expose the **Iceberg REST** API, so the same clients (PyIceberg, DuckDB, Trino, Spark) work against either. Apache Polaris is the ASF alternative with credential vending and fine-grained RBAC. |
| `pipeline/generate_raw.py` | GitHub Actions running `aws ec2 describe-instances` | same nested DescribeInstances schema, one file per region per 2 h, **zstd** |
| `pipeline/load_iceberg.py` | Airflow + EMR on EKS Spark | flatten with DuckDB, write with PyIceberg, **idempotent per-day overwrite**, day partitions + sort order |
| `api` (FastAPI + DuckDB) | RayService API | adds the hot cache, RS256/JWKS, scopes, token exchange |
| `mcp` (MCP SDK v2) | "exposed as an MCP tool somewhere" | OAuth resource server, 4 task-shaped read-only tools |
| OpenBao | Secrets Manager / Vault / IRSA | [09](09-secrets-openbao.md) |

## Data

- Raw: `s3://raw/ec2/describe_instances/region=<r>/dt=YYYY-MM-DD/hour=HH/describe_instances.parquet` —
  4 regions × 183 days (2026-04-01 … 2026-09-30) × 12 snapshots = **8,784 files**.
- Iceberg `ec2.instances`: **~2.0 M rows** (one per instance per snapshot), partitioned by `day(snapshot_ts)`,
  sorted by region/account/instance, zstd. Plus `ref.instance_types` (vCPU/memory/GPU per type).
- The fleet is simulated, not random: instances keep IDs over time and move through pending → running → stopped →
  terminated; ASGs follow daily curves; Spark runs at night on spot; a legacy Windows fleet is decommissioned around
  day 60-105; a new service launches in ap-southeast-1 on day 65.
- 8 accounts (one per team). The account the examples use, `392918273645`, is the platform team.

## Commands

```bash
mise run up        # build + start (OpenBao, S3, catalog, API, MCP); waits until healthy
mise run seed      # first time only: 6 months of data (~3-4 min on an idle laptop)
mise run test      # 17 tests against the running stack
mise run down      # stop, keep data          mise run reset   # stop and delete everything
mise run unseal    # after a Docker restart (OpenBao starts sealed)
```

Without mise: `docker compose up -d --build --wait api mcp && docker compose --profile seed run --rm seed`.

**Resources**: steady state is roughly 2-3 GB of RAM (API up to 2 GB with two workers, SeaweedFS up to 1.5 GB);
seeding adds up to 4 GB temporarily. The default 12 GB Docker VM is enough when this is the only stack running.

**Other projects reading this lakehouse** (they join the `ec2-lakehouse_default` network): Iceberg REST at
`http://lakekeeper:8181/catalog`, warehouse `lakehouse`, S3 at `http://seaweedfs:8333` (path-style). S3 keys are
generated by OpenBao — read them with the developer token:
`curl -s -H "X-Vault-Token: $(cat .bao/dev-token)" http://localhost:8200/v1/secret/data/ec2-lakehouse/s3`.
